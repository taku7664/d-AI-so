일곱 화면의 여백·폭·머리 구조가 제각각이라 탭을 옮길 때 내용이 흔들린다(§4).

그래서 WinUI가 이미 주는 골격(`TitleBar` · `NavigationView.Header`)으로 갈아엎고,
마지막에 테스트로 잠근다(§7 Stage 7).

### 일하는 방식

- **Stage 순서대로 한다.** 앞 단계의 완료 기준을 충족하기 전에 다음 단계를 시작하지 않는다
- **단계마다 커밋한다.** 한 화면이 깨지면 그 커밋만 되돌릴 수 있게. 커밋 뒤 `git push origin main`
- **완료 기준은 눈이 아니라 그림으로 확인한다:**

  ```powershell

  .\tools\shoot-screens.ps1           # 1024 · 1280 · 1600 × 일곱 화면을 artifacts\screens 에 찍는다
  ```

  고치기 전에 `-OutDir artifacts\before`로 한 벌 찍어 두고, 고친 뒤와 나란히 본다.
  창 하한이 1024라(§5.6) 1024는 **반드시** 포함해서 찍는다 — 지금 내 규칙이 이 폭에서 깨진다

- **§8의 결정은 다시 논의하지 않는다.** 버린 안과 이유가 거기 적혀 있다.
  바꿔야 할 근거가 새로 나오면 §8에 항목을 덧붙이고, 원래 결정을 지우지 말고 남긴다

## 1. 요약 — 결론부터

**첫 계획에서 `PageShell`이라는 공통 골격 컨트롤을 새로 만들자고 했는데, 그건 틀렸다.**
WinUI가 이미 그 자리를 갖고 있다. 우리가 그걸 안 쓰고 페이지마다 손으로 다시 짜서 어긋난 것이다.

| 지금 우리가 손으로 짠 것 | 플랫폼이 이미 주는 것 |
|---|---|
| 페이지마다 대제목 `StackPanel` | **`NavigationView.Header`** — 높이 52px 고정, 용도가 "선택된 항목의 페이지 제목", 본문 스크롤의 클리핑 지점 |
| 직접 그린 제목줄 `Grid` (로고 + "DAIso") | **`TitleBar` 컨트롤** (App SDK 1.8 정식) — 아이콘·제목·부제·뒤로 버튼·창 끌기 영역·`LeftHeader`/`RightHeader` 슬롯 |
| 본문 위에 겹쳐 띄운 뒤로/앞으로 | `TitleBar`의 내장 뒤로 버튼, 또는 `NavigationView.Header`의 오른쪽 자리 |
| 페이지마다 다른 여백(8·12·14·16) | 공식 권장 **본문 여백 24px** (Minimal 모드는 12px) |
| 페이지마다 다른 최대 폭(1280 / 없음 / 1280+왼쪽붙임) | PowerToys가 쓰는 방식 — **`PageMaxWidth` 리소스 하나**를 공용 페이지 컨트롤이 적용 |

그래서 계획을 **"공통 컨트롤을 새로 발명"에서 "플랫폼 골격으로 갈아엎기"로 바꾼다.**
새로 만드는 코드가 줄고, 규격이 우리 취향이 아니라 OS 표준이 된다.

## 3. 확인된 불일치 (증거)

### A. 페이지 골격 — 가장 큰 원인

| 화면 | 루트 | 행 간격 | 본문 최대 폭 | 최소 폭 |
|---|---|---|---|---|
| 요약 | `ScrollViewer` | 16 | **1280** | 720 |
| 사용량 | `ScrollViewer` | 16 | **1280** | 720 |
| 터미널 | `Grid` | **8** | 1280 (카드만, 왼쪽 붙임) | — |
| 세션 | `Grid` | **14** | **없음 (창 전체)** | — |
| 내 규칙 | `Grid` | **14** | **없음** | — |
| 내 프롬프트 | `Grid` | **14** | **없음** | — |
| 설정 | `Grid`+`ScrollViewer` | **12** | **1280** | 안쪽 820 |

행 간격 **네 가지**, 폭 정책 **세 가지**. 캡처에서 본문 오른쪽 끝이
요약·사용량·설정 x≈1512 / 세션·규칙·프롬프트 x≈1568 / 터미널 x≈1420으로 갈린다.
탭을 옮길 때 내용이 좌우로 흔들리는 게 이것이다.

또한 루트 패딩이 `24,20,24,20`이라 **위아래가 20으로 권장값 24와 다르다.**

### B. 대제목 줄 — 규칙을 세웠는데 두 화면이 안 지킴

- **요약**: `다시 읽기`가 아직 대제목 줄에 있고 **셸의 뒤로가기 화살표에 그대로 가린다** (캡처 확인)
- **내 규칙**: 명령 6개 + `⋯`가 대제목 옆에 붙어 있다

### C. 페이지 명령을 두는 방식이 다섯 가지

요약(버튼 1개) · 사용량(콤보+버튼) · 터미널(탭 띠) · 세션(아이콘 버튼 3 + 검색칸 + 콤보 3 + 알약) ·
내 규칙(아이콘+글 6 + 오버플로) · 내 프롬프트(`CommandBar`) · 설정(하단 바).

### D. 저장이 세 군데

설정은 **하단 바**, 내 규칙은 **상단 명령바**, 내 프롬프트는 **상단 버튼**. 편집 화면 셋이 다 다르다.

### E. 좌측 목록 폭 제각각

**내 규칙 218px · 내 프롬프트 278px · 세션 418px.** 끌어 조절되는 건 내 프롬프트뿐.

### F. 하단 줄이 두 겹

내 규칙·내 프롬프트는 페이지 안내 줄 + 그 아래 셸 상태바가 겹친다. 다른 화면엔 페이지 안내 줄이 없다.

### G. 그 밖

- 비어 있음 안내: `InfoBar`(사용량) vs 옅은 판(세션·규칙) vs 하단 한 줄(프롬프트)
- 카드: `CardBorder`(요약·사용량·설정) vs 테두리 없는 판(세션·규칙·프롬프트)
- 거르기: `SelectorBar` 탭(요약·사용량) vs 콤보박스(세션)
- 부제: 고정 설명(요약·프롬프트) vs 동적 상태값(사용량·세션)

## 4. 왜 이렇게 됐나

페이지가 각각 독립적으로 만들어졌고 **골격이 코드로 강제되지 않는다.**
`PagePadding`·`ContentMaxWidth`·`CardBorder` 같은 조각 리소스는 있지만 조립은 페이지마다 손으로 다시 짰다.
그래서 규칙을 문서에 적어도(§6.2) 요약·내 규칙처럼 빠지는 곳이 생긴다.

**고칠 대상은 각 페이지의 값이 아니라, 골격이 강제되지 않는다는 사실이다.**

## 5. 레퍼런스에서 가져올 것

### 4.1 창 골격 — `TitleBar` + `NavigationView.Header`

Fluent 지침은 커스텀 제목줄을 쓸 때 **뒤로 버튼과 창 메뉴 버튼을 제목줄에 두라**고 한다.
WinUI 3 Gallery가 쓰는 방식이고, `TitleBar` 컨트롤이 그걸 위해 존재한다.

```xml
<TitleBar Title="DAIso"
          IsBackButtonVisible="True"
          IsBackButtonEnabled="{x:Bind History.CanGoBack, Mode=OneWay}"
          BackRequested="OnBackRequested"
          IsPaneToggleButtonVisible="True"
          PaneToggleRequested="OnPaneToggleRequested">
    <TitleBar.IconSource>...</TitleBar.IconSource>
</TitleBar>

<NavigationView IsBackButtonVisible="Collapsed" IsPaneToggleButtonVisible="False">
    <NavigationView.Header> ... 페이지 제목 ... </NavigationView.Header>
    <Frame x:Name="ContentFrame" />
</NavigationView>
```

지금 앱은 `TitleBarArea`라는 `Grid`를 직접 그리고 있어 이 기능을 전부 손해 보고 있다.
`TitleBar`에는 앞으로 버튼이 없지만 **`LeftHeader` 슬롯**에 넣으면 된다.

### 4.2 페이지 제목 — `NavigationView.Header`

높이 52px 고정, 용도가 페이지 제목, **본문 스크롤의 클리핑 지점**.
여기로 옮기면 페이지가 대제목을 각자 그릴 일이 없어져 §3-B 같은 어긋남이 **구조적으로 불가능**해진다.

### 4.3 여백·폭 — 공식 권장값 + 공용 리소스

- 본문 여백 **24px** (Minimal 모드 12px). 지금의 `24,20,24,20`을 24로 맞춘다
- PowerToys는 `SettingsPageControl` 하나가 `PageMaxWidth` 리소스를 적용한다.
  우리도 폭을 **페이지가 정하지 않고 골격이 정한다**

### 4.4 2단 화면 — List/Details 지침

공식 지침은 **641epx 이상에서 나란히, 그 아래는 겹쳐 쌓기**를 권한다.
목록 칸 폭의 표준값은 정해 주지 않으므로 **우리 규약으로 한 값을 정하고 끌어 조절 가능하게** 한다.

### 4.5 같은 갈래 앱들

Claude Code 사용량·세션을 다루는 도구들(ccusage, tokenmeter, claude-usage, Claude Monitor, ClaudeWatch)은
공통적으로 **① 지금 얼마나 썼나 ② 한도까지 얼마나 남았나 ③ 세션 이력**을 앞세운다.
우리 요약·사용량 화면이 이 셋을 한눈에 주는지는 레이아웃 정리 뒤 따로 볼 문제로 남긴다 (이 계획의 범위 밖).

### 5.6 리사이즈 — 지금 정책이 "있긴 한데" 지켜지지 않는다

#### 지금 상태 (측정)

코드에 **정책이 이미 있다. 다만 문서에 없고, 지켜지지도 않는다.**

```csharp
// ShellWindow.xaml.cs
private const int MinimumWidth = 1024;
private const int MinimumHeight = 700;
// 사용자가 더 줄이지 못하게 창 자체의 하한을 준다. 레이아웃이 깨질 구간을 없앤다.
presenter.PreferredMinimumWidth = MinimumWidth;
```

즉 노선은 **"적응형을 만들지 않는 대신 깨지는 구간을 창 하한으로 막는다"**이다. 나쁘지 않은 선택이다.
실제로 창을 640까지 줄여 봐도 1024에서 멈춘다 (측정 확인).

그런데:

- **`AdaptiveTrigger`·`VisualState`가 저장소 전체에 0건이다.** 폭에 따라 바뀌는 것은 아무것도 없다
- **`PaneDisplayMode="Left"`로 못 박혀 있다.** 좌측 메뉴는 어떤 폭에서도 접히지 않는다
  (플랫폼 기본 `Auto`는 1008 미만에서 아이콘만, 640 이하에서 햄버거로 접는다.
  단 하한이 1024이므로 **지금 구성에서는 `Auto`여도 결과가 같다** — 이 못 박기는 하한과 짝이 맞는다)
- **하한에서 실제로 깨지는 화면이 있다.** 주석의 "깨질 구간을 없앤다"가 사실이 아니다

#### 하한(1024)에서 깨지는 것 — 캡처로 확인

**내 규칙**
- `⋯` 오버플로 버튼이 **뒤로/앞으로 화살표에 깔린다**
- "행동 문장" 입력칸이 **"행동 문"으로 잘린다**
- **"마크다운 미리보기" 칸이 창 밖으로 밀려나** 오른쪽이 잘린다

산수도 맞는다: 목록 220 + 본문 `MinWidth` 360 + 미리보기 `MinWidth` 190 = **770**,
여기에 좌측 메뉴 210 + 페이지 여백 48 + 열 간격 28 = **1056 > 1024**.
**하한이 이 화면의 실제 요구보다 32px 작다.**

**세션** — 대체로 버티지만 `Markdown 내보내기` 버튼이 상세 칸 오른쪽 끝에 닿는다.
요약·사용량·터미널·내 프롬프트·설정은 1024에서 이상 없다.

#### 정책 — "고정 하한 + 그 위는 유동"

적응형 상태를 여러 개 만드는 길(`PaneDisplayMode="Auto"` + 641에서 2단 접기)도 있지만,
이 앱은 개발자용 데스크톱 도구라 좁은 창에서 쓸 일이 거의 없다.
**상태를 늘리는 대신 하한을 지키는 지금 노선을 제대로 완성하는 쪽**을 택한다.
(*버린 안*: 완전 적응형. 상태마다 검증이 필요하고, 640px에서 이 앱을 쓸 사람이 없다.)

1. **창 하한은 1024×700을 유지한다.** 단 `ARCHITECTURE.md`에 적어 근거를 남긴다.
   적응형을 안 만드는 대가로 두는 것임을 명시한다 — 지금은 주석 한 줄에만 있다
2. **MUST — 모든 페이지는 하한에서 잘림·겹침 없이 들어간다.**
   페이지가 요구하는 최소 폭의 합(좌측 메뉴 210 + 여백 48 + 칸 최소 폭 + 간격)이 1024를 넘으면
   그 페이지가 틀린 것이다. 지금 내 규칙이 위반 중 → Stage 0에서 고친다
3. **하한 위에서는 유동이다.** 창을 넓히면
   - `Reading` 화면: 본문이 `PageMaxWidth`(1280)까지 자라고, 그 이상은 **왼쪽 정렬 + 오른쪽 여백**
     (지금 동작이 이미 이렇다. PowerToys도 왼쪽 정렬이다. 가운데 정렬로 바꾸지 않는다)
   - `Wide` 화면: 창을 다 쓴다
4. **SHOULD — 2단 화면의 목록 칸은 고정 폭이 아니라 `기본 / 최소 / 최대 + 드래그`.**
   남는 폭은 오른쪽 칸이 먹는다. 지금은 세션 420(320–900) · 프롬프트 280(180–560) · 규칙 220(180–480)으로
   기본값이 셋 다 다르고 드래그도 프롬프트만 된다. 기본값 하나로 맞춘다
5. **MUST — 세로는 한 곳만 스크롤한다.** 머리(제목·명령·필터)와 푸터는 스크롤하지 않는다.
   `Reading`은 본문 전체가 한 덩어리로, `Wide`는 칸마다 따로 스크롤한다
6. **SHOULD — 표·목록에서 고정 폭 열은 최소로 둔다.** 남는 폭은 이름·경로 열이 먹고
   `TextTrimming="CharacterEllipsis"` + 전체 문구 툴팁을 단다 (기존 §6.2 규칙과 같다)
7. **검증은 눈이 아니라 캡처로 한다.** 1024 / 1280 / 1600 세 폭에서 일곱 화면을 찍어 비교한다.
   캡처 스크립트를 `tools/`에 넣어 반복 비용을 없앤다

#### 이 정책이 단계에 미치는 것

- **Stage 0**에 "내 규칙이 1024에서 깨지는 것" 수정을 넣는다 (미리보기 칸을 접거나 최소 폭을 낮춘다)
- **Stage 3·4**의 완료 기준에 "1024에서도" 조건을 붙인다
- **Stage 7**의 테스트에 "페이지 최소 폭 합이 1024 이하" 검사를 넣는다

## 6. 목표 골격

```
┌─ TitleBar ──────────────────────────────────────────────┐
│ [뒤로][앞으로] [☰] 🅳 DAIso              — □ ✕          │  ← 창 제목줄
├─────────────┬───────────────────────────────────────────┤
│ 요약        │  사용량                        (Header 52px)│  ← 페이지 제목. 셸이 그린다
│ 사용량      ├───────────────────────────────────────────┤
│ 터미널      │  [명령 줄]        (없으면 줄이 사라짐)      │
│ 세션        │  [필터·탭 줄]     (없으면 줄이 사라짐)      │  ← 본문. 페이지가 그린다
│ 내 규칙     │                                           │     여백 24, 폭은 골격이 정함
│ 내 프롬프트 │  본문                                      │
│ 설정        │                                           │
│             ├───────────────────────────────────────────┤
│             │  [푸터 — 저장 바 / 안내]                    │
├─────────────┴───────────────────────────────────────────┤
│ 상태바 (인덱싱 진행)                                       │
└──────────────────────────────────────────────────────────┘
```

골격이 강제하는 것 (우선순위 MUST > SHOULD > MAY):

| | 규칙 | 등급 |
|---|---|---|
| 1 | **페이지는 대제목을 그리지 않는다.** 셸이 `NavigationView.Header`에 그린다 | MUST |
| 2 | **본문 여백 24 · 행 간격 12** 한 벌만 쓴다 | MUST |
| 3 | **본문 폭은 `Reading`(1280 상한, 왼쪽 정렬) / `Wide`(창 전체) 두 값뿐이다** | MUST |
| 4 | **모든 페이지가 창 하한 1024×700에서 잘림·겹침 없이 들어간다** (§5.6) | MUST |
| 5 | **세로 스크롤은 한 곳에서만.** 머리(제목·명령·필터)와 푸터는 스크롤하지 않는다 | MUST |
| 6 | **저장은 언제나 푸터** | MUST |
| 7 | 명령 줄 · 필터 줄 · 푸터의 **자리와 순서**를 지킨다 (없으면 그 줄이 사라진다) | MUST |
| 8 | 2단 화면의 목록 칸은 **`기본/최소/최대` + 드래그**. 남는 폭은 오른쪽 칸이 먹는다 | SHOULD |
| 9 | **도구별 거르기는 탭**(`SelectorBar`), 나머지 축은 콤보 | SHOULD |
| 10 | 표·목록의 고정 폭 열은 최소로. 남는 폭은 이름·경로가 먹고 말줄임 + 툴팁 | SHOULD |

1번이 이 계획의 핵심이다. 대제목을 셸이 그리면 "대제목 옆에 뭘 두는" 실수가 **구조적으로 불가능**해진다 —
규칙을 문서에만 적어 두고 요약·내 규칙에서 빠뜨린 이번 일이 재발할 수 없다.

페이지가 쓰는 얇은 컨트롤 하나(`PageBody`)만 남는다 — 대제목이 셸로 갔으므로 첫 계획의 `PageShell`보다 훨씬 작다.

## 7. 단계

각 단계는 그것만으로 빌드·테스트가 통과하고 앱이 돈다.

### Stage 0 — 지금 깨진 것 (작다, 먼저)
- 요약의 `다시 읽기`, 내 규칙의 명령바를 대제목 줄에서 아래로
- **내 규칙이 하한 1024에서 깨지는 것** — 최소 폭 합 1056을 1024 이하로 내린다
  (미리보기 칸 `MinWidth` 190을 낮추거나, 좁을 때 접는다)

**완료 기준**: 1024와 1600 두 폭에서 일곱 화면을 찍었을 때
대제목 오른쪽에 페이지 물건이 없고, 잘리거나 겹치는 것이 없다.

### Stage 1 — 창 골격 교체 (`TitleBar`) · 뒤로/앞으로 이사
직접 그린 `TitleBarArea` Grid를 `TitleBar` 컨트롤로 바꾼다.
- 뒤로 = `TitleBar` 내장 버튼 (`IsBackButtonVisible` / `IsBackButtonEnabled` / `BackRequested`)
- 앞으로 = `TitleBar.LeftHeader`에 버튼 하나
- `NavigationView`는 `IsBackButtonVisible="Collapsed"`, `IsPaneToggleButtonVisible="False"`로 중복 제거
- 본문에 겹쳐 그리던 오버레이 `StackPanel` 삭제
- `NavigationHistory`는 그대로 쓴다 (이미 셸 것이다)

**완료 기준**: 창 끌기·최대화·테마·Windows 10 제목줄이 그대로고,
**1024 폭에서도** 뒤로/앞으로가 어떤 화면의 내용도 가리지 않는다.

### Stage 2 — 페이지 제목을 셸로 (`NavigationView.Header`)
페이지가 제목·부제를 셸에 알리고(속성 또는 인터페이스), 셸이 Header에 그린다.
일곱 페이지에서 대제목 `StackPanel`을 걷어낸다.
**완료 기준**: 일곱 화면의 제목 기준선(y좌표)이 캡처에서 **모두 같다**.

### Stage 3 — `PageBody` + 여백·폭 통일
명령/필터/본문/푸터 슬롯, 여백 24, 행 간격 12, `Reading`/`Wide` 두 폭.
읽는 화면 3개(요약·사용량·설정)부터 이관.
**완료 기준**: 세 화면의 본문 좌·우 끝 x좌표가 캡처에서 **같다**.

### Stage 4 — 2단 편집 화면 3개 (세션·내 규칙·내 프롬프트)
`Wide` 폭. 저장을 전부 푸터로. 목록 칸 폭을 한 값으로 맞추고 셋 다 `PaneSplitter` 적용.
페이지 안내 줄을 푸터로 넣어 셸 상태바와 겹치지 않게.
**완료 기준**: 목록 폭·저장 자리가 같고, 하단 줄이 한 겹이다.

### Stage 5 — 터미널
방 화면 `Wide`. 새 세션 카드의 `HorizontalAlignment="Left"` 제거.
**완료 기준**: 일곱 화면 본문 오른쪽 끝이 두 값 중 하나다.

### Stage 6 — 낱개 통일
- 덩어리는 전부 `CardBorder`
- **세션의 도구 콤보를 `SelectorBar` 탭으로** (프로젝트·기간은 콤보 유지) — §8.4. 어색하면 이 커밋만 되돌린다
- 비어 있음 안내를 한 모양으로
- 부제 성격 통일 (고정 설명 vs 동적 상태값)

**완료 기준**: 항목마다 일곱 화면에서 같은 모양이 나온다.

### Stage 7 — 규칙을 테스트로 잠그기 (이 계획의 목적)
`Daiso.Core.Tests`에 XAML 검사를 추가한다. §6 표의 MUST만 검사한다:
- 페이지가 `PageTitleText`를 직접 쓰지 않는다 (1번)
- 페이지 루트가 `PageBody`다 (2·7번)
- 폭이 `Reading`/`Wide` 두 값 중 하나다 (3번)
- 페이지가 선언한 칸 최소 폭의 합 + 좌측 메뉴 210 + 여백 48 ≤ 1024 (4번)

`ARCHITECTURE.md` §6.2를 새 골격 기준으로 다시 쓴다. 창 하한 1024×700의 근거도 여기 적는다
(지금은 코드 주석 한 줄에만 있다).

**완료 기준**: 규칙을 어긴 페이지를 만들면 테스트가 빨개진다.

## 8. 결정 기록

전부 확정됐다. 뒤에 오는 사람이 같은 갈래를 다시 파지 않도록 **버린 안과 그 이유도 남긴다.**

### 7.1 뒤로/앞으로 자리 → **(b) `TitleBar` 왼쪽**

뒤로는 `TitleBar` 내장 버튼, 앞으로는 `LeftHeader` 슬롯.

*버린 안 — (a) `NavigationView.Header` 오른쪽 끝*: 처음 지시받은 자리였고 겹침도 해결된다.
버린 이유는 모든 화면에서 제목 줄 오른쪽을 영구히 비워둬야 하고(그게 이미 요약·내 규칙에서 사고를 냈다),
데스크톱 앱 중 그렇게 하는 사례를 못 찾았고, `TitleBar`로 갈아엎으면 뒤로 버튼이 공짜로 따라오기 때문이다.

### 7.2 본문 폭 → **`Reading` / `Wide` 두 가지**

- `Reading` = `PageMaxWidth`(1280) 상한, 왼쪽 정렬 — 요약 · 사용량 · 설정
- `Wide` = 창 전체 — 터미널 · 세션 · 내 규칙 · 내 프롬프트

*버린 안 — 전부 `Reading` 하나*: 값이 하나면 제일 단정하다.
버린 이유는 2단 편집 화면(목록+본문+미리보기)이 1280 안에서 답답해지기 때문이다.
§5.6에서 잰 대로 내 규칙은 최소 폭 합만 1056이라 여유가 거의 없다.

**두 값 중 하나여야 한다. 세 번째는 없다** — 지금 터미널의 "1280인데 왼쪽 붙임"이 세 번째였고, 그게 §3-A의 원인이다.

### 7.3 저장 자리 → **언제나 푸터**

설정·내 규칙·내 프롬프트 셋 다 하단 바로 통일한다. `Ctrl+S`는 그대로 둔다.

*버린 안 — 상단 명령바 유지*: 내 규칙·내 프롬프트는 지금 상단에 있어 옮기면 손이 다시 익어야 한다.
버린 이유는 편집 화면 셋의 저장 자리가 다른 게 §3-D이고, 셋 중 둘을 옮기든 하나를 옮기든
어차피 누군가는 다시 익혀야 하는데, 저장은 "다 하고 누르는 것"이라 아래가 자연스럽기 때문이다.

### 7.4 세션의 도구 필터 → **`SelectorBar` 탭으로**

요약 · 사용량 · 터미널이 모두 도구별 탭을 쓴다. 세션만 콤보인 것을 맞춘다.
프로젝트 · 기간은 콤보로 남긴다.

**규칙: 도구별 거르기는 탭, 나머지 축은 콤보.**

*위험*: 세션에서 도구는 세 필터 중 하나일 뿐이라, 탭으로 올리면 다른 둘보다 중요해 보인다.
그래서 되돌리기 싼 **Stage 6에 둔다.** 실제로 써 보고 어색하면 콤보로 되돌린다.

### 7.5 어디까지 → **Stage 7까지 전부**

*버린 안 — Stage 5에서 멈추기*: 5까지면 "너비가 다르다"는 사라진다.
버린 이유는 이 문제의 원인이 §3에서 짚었듯 **"골격이 코드로 강제되지 않는다"**는 것이고,
Stage 7(테스트로 잠그기)이 그 원인을 없애는 유일한 단계이기 때문이다.
7이 없으면 규칙을 문서에 적어 두고 또 빠뜨린다 — 이미 이번에 요약·내 규칙에서 그렇게 됐다.

## 9. 위험과 되돌리기

- **Stage 1이 가장 위험하다.** 제목줄 교체는 창 끌기·최대화·테마·Windows 10 제목줄 색 문제와 얽힌다
  (`ARCHITECTURE.md`에 Windows 10은 제목줄 색 API가 없다는 기록이 있다). 이 단계만 따로 커밋하고 먼저 검증한다
- Stage 2~5는 페이지별로 커밋을 쪼갤 수 있어, 한 화면이 깨지면 그 커밋만 되돌리면 된다
- 각 단계 끝에 일곱 화면을 다시 캡처해 좌표로 비교한다 (`tools/`에 캡처 스크립트를 넣어 두면 반복이 싸진다)
